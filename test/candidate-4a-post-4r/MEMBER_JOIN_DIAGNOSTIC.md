# Candidate 4A member-create diagnostic — E2 owner decision accepted for final local gate

The earlier sections below preserve the diagnostic sequence, including the initially blocked state. On 2026-09-30 the owner accepted **E2** narrowly: an existing, independently verified parent; correct DENY; and the same `evaluation error ... false` pattern on exact post-4R baseline Rules do not alone block Candidate 4A. Baseline parity was reproduced for foreign-root, note, photo, file, and member denied paths. A later audit proved that line-based whitelisting alone was insufficient: the 4A-only DENY for owner title edit on a deleted root emits the same line's diagnostic, while the exact post-4R baseline ALLOWS that edit. A strict test now blocks this unapproved candidate-only diagnostic. The final local gate remains FAIL, and no commit was made. This does not change Rules or classify the historical image incident.

## Final standalone isolation (subsequent diagnostic turn)

The independent fixture `minimal-parent-read/minimal.rules` and `minimal-parent-read.test.mjs` has only `/parents/{id}` and `/parents/{id}/members/{uid}`. Firebase Admin SDK 12.7.0, pinned explicitly to `FIRESTORE_EMULATOR_HOST=127.0.0.1:8412`, seeded and read the parent immediately before every Rules request. No production service was contacted. Versions: firebase-tools 15.31.0; Firestore emulator JAR 1.22.0; `@firebase/rules-unit-testing` 3.0.4; Firebase client SDK 10.12.5. No local release note conclusively identifies this diagnostic behavior as a known version issue.

All four forms — direct `get(parent).data.status`, `exists(parent) && get(parent).data.status`, a helper/local `let parent=get(parent); return parent.data.status`, and an `exists` + `data.keys().hasAll(['status'])` guard — produced the same authorization matrix: existing/open ALLOW, existing/closed DENY, missing DENY. For existing/closed, the emulator reports `evaluation error ... false for create`; Admin SDK confirms the parent exists and status is `closed`. For missing, unguarded direct/helper forms additionally report `Null value error`; guarded forms do not. Coverage emits bare `undefined` values even on an allowed open request, so bare `undefined` is not proof that the existing parent vanished. A real null dereference is distinguishable by `causeMessage: Null value error.`

The existing-parent `closed`/`deleted` diagnostic is therefore classified **E2 — emulator/coverage diagnostic artifact on a correct DENY**, not a Candidate 4A regression or evidence of a missing production parent. The wording appears in emulator debug output and the denied request's error message, not only in coverage; the artifact is the extra `evaluation error` label alongside the actual false authorization result. The precise emulator internal reason for this extra label is not established.

Separate baseline safety observation: clients can address `groupActivities/{activityId}/members/{uid}` even when the parent document does not exist. The baseline `groupActivityData(activityId).keys()` / `.status` dereference then can genuinely hit a null parent; the same request still fails closed. This is **not** the cause of the existing-parent 4A blocker. Do not change baseline Rules under this 4A diagnostic scope; if the owner wants clean logging for orphan paths, review a guarded baseline-level change separately.

Suggested strict-gate acceptance rule for owner decision: do not fail Candidate 4A solely for a baseline-identical `evaluation error ... false` on an otherwise correct DENY when the parent is independently proven to exist and no `Null value error`, permission mismatch, expression-limit, or access-call-limit is present. Continue failing on new/candidate-only diagnostics, real null cause messages in expected existing-parent flows, or wrong authorization. This is a documented proposal only; the Candidate 4A strict runner and Rules have not been relaxed for release.
